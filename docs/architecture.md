# Как устроен GuestPass

## Маршрут запроса

Telegram доставляет update процессу `app.bot`. Бот берёт ID из `message.from_user.id` или `callback_query.from_user.id`, а не из пересланного сообщения. Через внутренний HTTP API он обращается к `app.api`. API проверяет сервисный ключ и область доступа организатора. `GuestService` выполняет операции с PostgreSQL.

Веб-панель использует те же методы сервиса. Вход начинается с проверки `Telegram.WebApp.initData` на сервере. Сессия подписана отдельным назначением HMAC и живёт час. HttpOnly cookie используется в обычном WebView; в окружениях с ограничением сторонних cookie заголовок Authorization хранится только в памяти страницы.

## Подпись пропуска

В строке `GP1.` находится base64url от бинарных данных: версия, UUID события, UUID гостя, случайный nonce, срок действия и 32 байта HMAC-SHA256. Длина кода — 123 символа. Имя и Telegram ID в QR не записаны. Подпись проверяется через `compare_digest`. После криптографической проверки проверяются событие, nonce и срок в базе.

Токен является предъявительским пропуском: владелец скриншота может показать его на входе. Подпись защищает от подделки, но не заменяет проверку имени организатором.

## Одно начисление при конкуренции

Запись в `point_entries` уникальна по `(event_id, guest_id, kind)`. Начисление — один `INSERT ... ON CONFLICT DO NOTHING RETURNING id` в транзакции. Нет последовательности «прочитать баллы → проверить флаг → записать баллы», которая могла бы дать гонку. Проигравший конкурентный запрос возвращает `awarded=false`, победивший — `true`. Сумма баллов вычисляется из журнала, отдельного счётчика нет.

## Общее демомероприятие и доступ

В деморежиме `/start` собирает фамилию и имя, сохраняет гостя в основной встрече и выдаёт QR этой встречи. `/review` активирует для Telegram ID роль организатора **той же встречи** в `review_spaces`. Все проверяющие видят общие счётчики и могут сканировать пропуска всех участников. Два вымышленных гостя добавляются идемпотентно: повторный `/review` не создаёт их заново.

Это осознанно публичный демонстрационный режим: бот предупреждает, что имена видны другим проверяющим. `REVIEW_ENABLED=false` отключает получение роли через `/review` и игнорирует старые активации. В закрытом режиме действует только `ORGANIZER_IDS`. `/event` снимает самостоятельную роль проверяющего; доверенный ID сохраняет доступ.

Ранний вариант создавал личные стенды. При переходе на общую встречу старые подписанные QR **синтетических** гостей таких стендов разрешаются в общих тестовых гостей. Для этого проверяются подпись, событие, nonce и срок старого пропуска, а также принадлежность события к прежнему review-пространству. Произвольные чужие мероприятия не принимаются. Этот переход выключен вместе с публичным review-режимом.

## Оформление QR

ImageGen создал только фон билета. `make_pass_image` добавляет имя и настоящий QR. Печатаются только тёмные модули кода: светлая бумага видна между ними. Вокруг оставлена свободная quiet zone. ZXing-C++ распознаёт как чистый QR, так и оформленный билет. Тест проверяет несколько случайных токенов, уменьшение до 540×720 и JPEG quality 55.

## Где читать код

- `security.py`: генерация и проверка пропусков, Telegram initData и сессий.
- `schema.sql`: ограничения и журнал начислений.
- `service.py`: транзакции, области событий и тестовые стенды.
- `api.py`: HTTP-контракты и проверка доступа.
- `bot.py`: команды, картинки, карточки и callback-кнопка.
- `qr.py`: PNG-генерация и распознавание через ZXing-C++.
- `tests/test_integration.py`: реальные запросы к PostgreSQL, конкуренция и общие регистрации и запрет публичного доступа в закрытом режиме.

Схема для первой версии применяется идемпотентным SQL под PostgreSQL advisory lock при старте API. Для последующих изменений схемы нужны версионные миграции. Категория самостоятельного участника — «Гость», у двух вымышленных гостей — «Тестовый гость».
